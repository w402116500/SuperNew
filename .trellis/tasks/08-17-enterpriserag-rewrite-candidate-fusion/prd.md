# EnterpriseRAG 改写候选融合单变量评测

## 目标

验证一个明确的检索改动能否补齐现有改写检索分支丢失的证据：当首次检索证据不足、系统已按现有规则改写并再次检索时，保留两次检索的候选材料，去重后统一筛选最终 8 段，而不是让第二次结果覆盖第一次结果。

用户价值是减少“第一次已经找到部分关键材料、第二次换个问法后反而把它丢掉”的情况，同时不让普通问题增加额外搜索步骤。

## 已确认事实

- 父任务 `08-15-enterpriserag-english-formal-evaluation` 的 T7 基线和 T8 analysis 人工复核已完成；T9 尚未开始。
- 正式基线为 `baseline-rag-010`，仅使用 EnterpriseRAG 英文 Representative 语料和隔离集合 `rag_eval_enterpriserag_enterpriserag_en_representative_sf_001`。
- 当前简单问题在证据不足时已最多执行一次 Step-back 或 HyDE 改写；改写后的检索结果会覆盖首次结果。
- 在固定 300 道 analysis 题中，15 道实际触发了这条改写分支；其中 13 道自动归为 `retrieval_miss`，14 道自动判为 `fail` 或 `review`。
- 人工确认的 7 道“证据上下文/组织失败”和 4 道“证据不完整”均未触发改写分支，不能作为本次小范围试跑的题目。
- 500 题基线的改写触发率为 4.2%，因此普通问题不应受到本次改动影响。

## 范围

### R1：候选融合行为

- 仅在已有的“证据不足 -> 改写 -> 再检索”路径启用候选融合。
- 两次检索各自仍使用冻结的 Hybrid、每次候选池、分块、Auto-merging 和 Rerank 配置。
- 合并时按稳定 `chunk_id` 去重；再以原始用户问题统一执行现有 Auto-merging、Rerank 和最终 `top_k=8` 筛选。
- 不把两批最终文档直接拼接给回答模型，不增加最终上下文大小。
- 第二次检索或融合异常时，保留首次检索的可用结果并记录降级原因，不能因融合失败丢失已有证据。

### R2：评测隔离与审计

- 新行为由 `RetrievalRuntime` 的显式开关控制，默认关闭；线上默认知识库问答保持原行为。
- T9 只复用已冻结的 Representative 集合，不重新入库、不清理集合、不接触 `tutorial_verify_embeddings`。
- 每次 T9 运行保存新 `evaluation_id`、`changed_variable=rewrite_candidate_fusion`、配置快照、逐题 JSONL、汇总、报告和人工复核记录。
- trace 和报告记录首次候选数、改写候选数、去重后候选数、最终文档来源和融合是否降级；不得写入密钥。

### R3：固定小范围门槛

- 在改代码前，从 `baseline-rag-010` 的 analysis trace 固定 15 道实际触发改写的题目清单及其哈希；禁止按新结果重新挑选题目。
- 小范围试跑首先检查关键材料和证据覆盖是否改善，同时记录回答判定、系统错误/超时和延迟。
- 只有满足以下条件才运行完整 300 道 analysis：至少 3 道题证据覆盖提升；没有新增系统错误或超时；证据覆盖下降不超过 1 道且有人工说明。
- 15 题试跑是排错门槛，不得作为正式性能结论或 validation 泛化结论。

### R4：完整分析与盲态保护

- 小范围通过后，以新的 evaluation ID 运行固定 300 道 analysis，逐题对比 `baseline-rag-010`。
- 200 道 validation 的题目、答案、失败详情和人工结论继续保持隐藏；在 analysis 结果确认前不得运行 validation。
- T9 结论必须区分“证据变完整”“回答变正确”和“延迟变化”，不能只报单一通过率。

## 范围外

- 改模型、Embedding、分块、top-k、候选池配置、Auto-merging 阈值、Rerank 配置或回答提示词。
- 让所有问题固定执行双重搜索。
- 重新准备语料、重新写入 Milvus、清理独立集合或操作默认业务集合。
- 直接上线到日常知识库问答。
- 在 T9 完成前运行 Challenge 完整 RAG 或 validation。

## 验收标准

- [ ] 默认检索路径与现有行为一致；只有显式启用开关且已触发改写时才执行融合。
- [ ] 候选按 `chunk_id` 去重，最终 Rerank 使用原始问题，最终上下文仍不超过 8 段。
- [ ] 改写失败或第二次检索失败不会覆盖首次可用证据，并有可审计的 trace。
- [ ] 15 道固定 analysis 清单可由基线运行和哈希复现，且拒绝包含 validation ID。
- [ ] 小范围与完整 analysis 都保存独立配置、运行编号、逐题 JSONL、汇总与人工复核记录。
- [ ] validation 细节不出现在自动报告或人工可读复核文件中。
- [ ] 相关单元测试、Python 编译和 `git diff --check` 通过。
