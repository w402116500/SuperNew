📐 RRF (Reciprocal Rank Fusion) 排名倒数融合原理

Mathematical Rigor

传统打分加权（如 0.7*dense + 0.3*sparse）受两路检索得分量纲、分布方差不一致影响，极其不稳定。SuperMew 采用 RRF (倒数排名融合)，纯基于两路结果的相对位次进行稳定融合：

RRF_Score(d) = Σm ∈ {dense, bm25} [ 1 / (60 + rankm(d)) ]
  • k = 60：经工程调优的平滑常数，有效消除前三名之后分数的断崖式下跌，防止单一检索器的长尾误命中主导最终排序。
  • 兼顾语义与精确字面：当用户搜索“B-204 号文件第三条”时，即使语义向量发生漂移，BM25 第一名也能以大分值将目标直接推入 Top 候选。

💡 为什么放弃应用层 BM25，全面转向 Milvus 2.5 原生

Engineering Choice
  • 零额外内存开销：应用层自建 rank_bm25 需将数百万 Token 词典与倒排表常驻每个 Python Worker 内存，极易导致 OOM。
  • 分布式倒排索引：Milvus 2.5 服务端在集合 Schema 中注册 bm25_function = Function(..., function_type=FunctionType.BM25)，文本写入时自动分词并建立倒排索引。
  • 事务与数据一致性：向量与全文索引共存同一物理集合，插入、删除、更新具备强一致原子性，彻底解决“向量库删了但内存 BM25 没删”的脏检索问题。

🔀 LangGraph Send 算子与 operator.add 机制深度剖析

State Reducer Design

传统多 Agent 框架常采用嵌套循环，无法并行且容易丢失局部状态。SuperMew 利用 LangGraph 核心特性：

  1. 条件边动态返回 Send 对象：_fanout_sub_questions 根据拆分出的子问题列表，动态返回 [Send("rag_sub_agent", {"sub_question": q}) for q in sub_questions]。
  2. 并发非阻塞执行：LangGraph 引擎在同一 Step 内并发调度执行各个 rag_sub_agent 实例，网络 I/O 完美重叠，响应耗时从 3x 压缩至 1x。
  3. 无锁原子聚合 (State Reducer)：通过为 retrieved_docs 指定 operator.add，各个子 Agent 返回的局部文档集在汇聚到 synthesis 节点时由框架自动完成合并，零并发锁争用。

Pydantic Model

class EvidenceGrade(BaseModel):
    # 检索片段与原始问题的主题契合度
    relevance: Literal["none", "weak", "strong"]
    
    # 证据是否足以支持生成完整、确定性回答

⚖️ 路由决策矩阵与优先级仲裁

Deterministic Routing
评估结果特征 最终执行路由 状态机转移与行为
answerability == "sufficient" answer 直接流向生成节点，组装带有真实标号 [1], [2] 的严谨答案。

🔄 Step-back 与 HyDE 改写互斥决策机制

Single-Loop Protection

Step-back 抽象概念提问 (适用于多条件/原则类问题)

当原始提问过于细碎（如“技术部周五加班订外卖怎么报销”），BM25 易受生僻字干扰。系统自动退后一步，生成更高阶的宏观原则问题（如“研发技术中心加班餐饮补贴管理办法与报销流程”），从 L1 章节大块召回宏观规定。

HyDE 假设性文档生成 (适用于专业术语/短查询)

当用户输入高度精简的短语（如“2026年年假折算”），利用 LLM 迅速生成一段包含行业通用术语的标准公文假想段落（Hypothetical Document），再送入 BGE-M3 生成稠密嵌入，显著拉近与实际语料的向量距离。

⚠️ 防死循环铁律：严格单次改写熔断

业内很多 RAG 系统因允许多次反思循环，导致在遇到语料库中不存在的知识时陷入 3-5 次持续改写，造成请求超时（超 60 秒）并浪费巨额 Token。SuperMew 在图状态中硬编码 state["rewrite_count"] < 1，改写一次后若仍未命中即直接走向澄清或优雅拒答，全链路耗时严格可控。

📐 RRF (Reciprocal Rank Fusion) 数学机理与量纲归一化优势 Mathematical Proof
对比维度 线性加权评分 (Linear Score Fusion) SuperMew RRF 倒数排名融合 (k=60) 工程设计优势
分数分布敏感性 极度敏感。Cosine 相似度通常集中在 [0.6, 0.95]，而 BM25 得分在 [0, 45+] 之间，极难找到全局适用的固定归一化系数。 完全不依赖原始分数值。仅依赖文档在各路检索中的相对排序位置（Rank），彻底消除量纲差异。 多路召回分布发生漂移时，系统融合表现依然保持高度稳定。
长短文本偏好 BM25 对短文本关键词高频重复有异常高的打分奖励，导致短无用段落压制语义长段落。 平滑常数 $k=60$ 有效抑制极值影响：第一名得分 $\frac{1}{61} \approx 0.01639$，第二名得分 $\frac{1}{62} \approx 0.01613$，平缓单调递减。 即使 BM25 产生极端偶发高分，也无法绝对统治最终前 Top-8 排序。
双路联合命中收益 若两路得分不协调，单路高分往往会掩盖双路都中等命中的高可信文档。 两路均命中的文档（如 Dense 第 3 名 + BM25 第 4 名）累计得分 $\frac{1}{63} + \frac{1}{64} \approx 0.0315$，将直接反超单路第 1 名。 精准提拔“语义相关且关键词严密吻合”的真正黄金切片。

⚡ Milvus 2.5 原生服务端 BM25 Function 与混合检索架构实现 Native Milvus 2.5
告别应用层维护 BM25，迈向 Milvus 2.5 原生全文检索时代
传统 RAG 方案通常在 Python 内存或 Elasticsearch 中额外维护 BM25 倒排索引，面临双写不一致、内存暴涨、跨网络合并繁琐等重大痛点。SuperMew 全面拥抱 Milvus 2.5，利用其内建的 FunctionType.BM25，在数据写入时由向量引擎自动分词并构建稀疏索引，极大简化了运维复杂度并提升了检索吞吐。 
def init_milvus_hybrid_collection(collection_name: str = "supermew_chunks"):
    """在 Milvus 2.5 中定义支持 Dense 向量 + 原生 BM25 稀疏索引的统一集合。"""
    schema = CollectionSchema(fields=[
        FieldSchema(name="chunk_id", dtype=DataType.VARCHAR, max_length=64, is_primary=True),
        FieldSchema(name="doc_id", dtype=DataType.VARCHAR, max_length=64),
        FieldSchema(name="chunk_level", dtype=DataType.INT16),
        FieldSchema(name="parent_chunk_id", dtype=DataType.VARCHAR, max_length=64),
        FieldSchema(name="text", dtype=DataType.VARCHAR, max_length=4096, enable_analyzer=True),
        FieldSchema(name="dense_vector", dtype=DataType.FLOAT_VECTOR, dim=1024),
        FieldSchema(name="sparse_vector", dtype=DataType.SPARSE_FLOAT_VECTOR)
    ], enable_dynamic_field=True)

    # 声明内建 BM25 Function：文本写入时自动由 Milvus 服务端生成稀疏向量
    bm25_func = Function(
        name="bm25_function",
        function_type=FunctionType.BM25,
        input_field_names=["text"],
        output_field_names=["sparse_vector"]
    )
    schema.add_function(bm25_func)

    # 建立稠密 HNSW 索引与稀疏倒排索引
    client.create_collection(collection_name=collection_name, schema=schema)
    client.create_index(collection_name, field_name="dense_vector", 
                        index_type="HNSW", metric_type="COSINE", params={"M": 16, "efConstruction": 200})
    client.create_index(collection_name, field_name="sparse_vector", 
                        index_type="SPARSE_INVERTED_INDEX", metric_type="BM25")

def _call_rerank_service(query: str, candidates: List[Document], timeout_s: float = 90.0) -> List[Document]:
    """调用外部 Qwen Reranker 精排服务，配备毫秒级超时检测与无损容灾降级。"""
    if not candidates:
        return []
    
    url = f"{os.getenv('RERANK_BINDING_HOST', 'http://127.0.0.1:8001')}/v1/rerank"
    payload = {
        "model": os.getenv("RERANK_MODEL", "Qwen/Qwen2.5-7B-Instruct"),
        "query": query,
        "documents": [doc.page_content for doc in candidates],
        "top_n": RETRIEVAL_TOP_K
    }

    try:
        resp = requests.post(url, json=payload, timeout=timeout_s)
        resp.raise_for_status()
        data = resp.json()
        
        # 按精排打分降序排列
        ranked_docs = []
        for item in data.get("results", []):
            idx = item["index"]
            score = item["relevance_score"]
            if score >= float(os.getenv("RERANK_MIN_SCORE", 0.45)):
                doc = candidates[idx]
                doc.metadata["rerank_score"] = score
                ranked_docs.append(doc)
        return ranked_docs

    except (requests.exceptions.Timeout, requests.exceptions.ConnectionError) as exc:
        # 核心容灾降级：记录告警日志，保留原始 RRF 排序输出，严禁业务报错中断
        logger.warning(f"Rerank service failed/timed out ({exc}), falling back to raw RRF ordering")
        return candidates[:RETRIEVAL_TOP_K]
