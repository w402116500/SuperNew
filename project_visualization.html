🌐 DataPilot: 受控数据分析 Agent 架构全景 Production-Ready

DataPilot 是一个专为严肃企业级数据分析打造的自主受控 Agent 系统。与市面上简单依靠 LLM 裸生成代码并盲目执行的 Demo 不同，DataPilot 确立了“模型按需选工具，系统管安全边界”的核心原则，通过深度融合 LangGraph ReAct 状态机、SQLGlot AST 语法树安全护栏、Docker 零网络沙箱 与 基于证据绑定的事实校验器，彻底解决了企业在数据智能分析中面临的“模型写死循环、越权删库、数据外泄、捏造统计数据（幻觉）”等痛点。

🏛️ 四大核心架构设计哲学

1. 动态循环 vs 僵化 Pipeline
拒绝硬编码三步走（查表->写SQL->调Python）。现实业务分析是非线性的：可能只需 SQL 直接出结论，也可能需要多轮 SQL 下钻再转 Python 出图，甚至在 SQL 语法错误时具备自我修复能力。系统只管约束工具边界，把调度决策权交给模型原生 Tool Calling。
2. 串行执行与确定性状态机
绝不使用 LangGraph 默认的并行 ToolNode。数据分析工具调用前后存在强烈的因果数据依赖（例如 Python 依赖 SQL 输出）。按顺序串行执行保证每一步状态原子累加，且能在每一个工具执行前精准响应用户的协作式取消信号。
3. 严禁幻觉的事实校验护栏
大模型最致命的问题是“查询结果是对的，但总结文本在瞎编”。DataPilot 设计了按分析计划启用的 commit_analysis_claims 证据工具与 fact_validator 模块，要求证据型分析将核心事实绑定到具体查询证据，并在输出前用高精度 Decimal 进行数字与表格核验。
4. 事务级账本与零丢失 SSE 流
坚守“先入库，后通知”的 Event Sourcing 思想。所有工具调用、执行耗时、错误日志先写入数据库（依托 UNIQUE(run_id, seq) 强行锁序），再广播至 SSE。前端即使遭遇网络抖动断连，依托 Last-Event-ID 即可完美增量重放，杜绝状态不一致。

❓ 为什么不采用市面上常见的“固定写死 Pipeline”？

历史上常见的做法是硬编码固定三步走：[1. 查表元数据] ➔ [2. 生成并执行 SQL] ➔ [3. 调 Python 画图/总结]。当前 DataPilot 采用 Opening 后的动态工具循环，下面保留这段对比来说明为什么不把它作为现行实现：

  • 业务分析场景的高度不确定性：用户问“我们上季度退货率最高的产品是哪个？”，只需要执行一条包含 ORDER BY ... LIMIT 1 的 SQL 即可直接给出答案，根本不需要执行 Python 沙箱；如果强制走三步，会徒增数秒延迟与 Token 消耗。
  • 多轮下钻与探索性分析：用户问“分析为什么华东区利润下滑？”，模型通常需要先查各品类利润分布，发现是数码类下滑后，第二轮再针对数码类按月份展开明细。固定三步走无法支持这种“观察数据后自适应调整查询”的探索能力。
  • 可修复错误的受控 Repair：方言语法或字段不存在等可修复错误可在预算内进入下一轮；权限、安全阻断和不可重试错误必须立即停止，不能被包装成普通观察继续执行。

🛠️ 状态机受控工具箱矩阵 (Controlled Toolset Matrix)

在 execute_tool 节点中，模型绝不是随意执行宿主机指令，而是由 _build_run_local_tools 动态注入当前 Run 绑定的 4 大受控工具（定义于 contracts.py: AgentToolName）。每个工具都具有独立的 Pydantic 入参强校验 Schema、沙箱隔离级别与安全审计：

1. run_sql_readonly AgentToolName.SQL

核心职责：在当前 Run 绑定的不可变数据源上，执行经过语法树白名单校验的只读 SQL 统计与聚合查询。

入参 Schema (_SqlArguments)：
• sql: str：只读 SQL 查询字符串（最大 8KB）。
• requirement_ids: list[str]：本次查询支撑的用户需求编号（如 R1）。
• assertion_ids: list[str]：对应的细粒度断言编号（如 R1.A1）。
安全与守卫机制： SQLGuard 基于 SQLGlot 进行 AST 深度解析，拦截所有 DDL/DML 与危险函数，强制追加 LIMIT 200/1000 窗口截断，自动脱敏敏感字段，并支持语法报错最多 3 次针对性 Auto-Repair 纠错自愈。
2. run_python AgentToolName.PYTHON

核心职责：在严格隔离的轻量 Docker 容器内执行复杂统计计算、高级算法分析与图表可视化渲染（如 Matplotlib/Seaborn）。

入参 Schema (_PythonArguments)：
• script: str：完整的可执行 Python 脚本（最大 256KB）。
• output_paths: list[str]：严格限制于 charts/*.png、outputs/ 等受白名单校验的文件。
• purpose: str：本次脚本执行的业务目的说明。
安全与守卫机制： 8 重 Docker 沙箱绝缘：--network none（物理断网）、--cap-drop ALL（剥离全部 Linux 特权能力）、只读根文件系统、只读挂载工作区、内存硬限制 512MB、单核 CPU 限制、非 root 用户运行（UID 10001）、30 秒硬超时，彻底消除反弹 Shell 与挖矿等主机逃逸风险。
3. explore_datalink AgentToolName.DATALINK

核心职责：按需动态检索并探索多源异构元数据知识图谱，精细加载特定表结构、字段含义、主外键关联路径与业务指标血缘。

入参 Schema (_DataLinkArguments)：
• query: str：语义检索关键词或实体名称（最大 2KB）。
• focus: Literal["schema", "data_profile", "join_paths"]：检索侧重模式（表结构/数据轮廓/关联路径）。
• max_nodes: int：单次返回的图节点上限（默认 12，最多 50）。
安全与守卫机制： 基于 FastMCP 协议挂载，操作只读图快照版本（datalink_graph_version）；局部子图按需加载，坚决杜绝把上千张表的全量 DDL 填鸭式灌入 Context，节省 80%+ 的上下文开销并提高检索准确率。
4. commit_analysis_claims AgentToolName.ANALYSIS_COMMIT

核心职责：分析结论与数值提交门禁。强制模型在生成最终回答前，将推导出的结论与量化指标显式绑定到真实的工具执行证据（EvidenceBinding）上。

入参 Schema (_AnalysisCommitArguments)：
• claims: list[_AnalysisClaimInput]：结构化量化主张列表。
  - requirement_id：绑定的需求编号（如 R1）。
  - evidence_binding_ids：引用的工具执行证据 ID（如 E1）。
  - values: list[FactValue]：提取的关键标量数值、单位与维度标签。
安全与守卫机制： 反数据幻觉第一道闸门：运行时强校验模型声明的 value 是否确实存在于前序 SQL/Python 执行生成的 ToolMessage 中。若发现未经验证的值、数值误差超标或凭空捏造，直接抛出异常拒绝接收，强迫模型重新核算。

❓ 为什么必须是“串行工具执行”，而绝不能使用 LangGraph 默认的并行 ToolNode？

LangGraph 官方标准库提供了一个 ToolNode，默认会将大模型在单轮中输出的多个 tool_calls 并发异步执行（asyncio.gather）。在数据分析 Agent 中，这会引发致命的系统级隐患：

1. 强因果数据流依赖
分析类工具前后具有强因果关系。例如模型单轮同时要求“执行 SQL 查月度收入”和“运行 Python 绘制走势折线图”，Python 代码必须等待 SQL 执行生成的 CSV 写入工作空间后才能读取。若并发执行，Python 必然因找不到文件而崩溃。
2. 状态机单向原子更新
串行执行确保每次工具执行完毕后，执行产物、报错计数器、证据引用（evidence_refs）等状态都在主线程中有序累加，彻底消除了并发写入 State 带来的竞态条件（Race Condition）与脏数据污染。
3. 毫秒级协作式取消响应
每一个工具调用循环体内部都显式植入了 _ensure_active(cancellation) 检查。当用户点击前端“停止生成”或超时触发时，系统在进入下一个工具前能毫秒级切断，而不是必须等待整批昂贵的工具并行跑完。

❓ 为什么模型停止请求数据工具后，必须进入独立的 Final Answer 节点？

在标准的 ReAct 循环中，很多初学者直接让 Agent 在无 ToolCall 时把最后一句输出当作给用户的回答。这种做法在企业级场景下存在极大隐患：

  • 上下文蒸馏与隔离：中间的 Agent 循环为了调试与纠错，可能加载了大量带有重试记录、SQL 调试输出、临时报错的脏上下文。final_answer 节点作为一个独立阶段，会根据已绑定的结构化 Evidence 重新精炼提示词，保证输出给用户的 Markdown 规范、专业且条理清晰。
  • 事实核验拦截关卡（Gatekeeper）：在 final_answer 节点内部，系统强制介入 fact_validator 事实校验器。大模型生成的正文数值与 Markdown 表格必须逐一与数据网关返回的真实标量进行 Decimal 精度比对。一旦发现模型捏造数字，立即打标拦截，降级输出安全兜底文本，绝不让虚假数据流出到前端！

        await _emit(dependencies.events, RunEventCreate(type=RunEventType.TOOL_CALLED, ...))

        tool_messages.append(observation.message)

即使 Python 运行了 while True: pass 导致 CPU 跑满，通过宿主机 Docker Daemon 强制发送内核信号将其瞬时击毙。 

async def terminate_docker_container(container_id: str):
    loop = asyncio.get_running_loop()
    try:
        # 1. 第一步: 软终止（给予 2 秒清理缓冲）
        cmd_term = ["docker", "kill", "--signal=SIGTERM", container_id]
        await run_cmd_async(cmd_term, timeout=2.0)
    except TimeoutError:
        # 2. 第二步: 死循环硬制裁（内核级强杀）
        logger.warning(f"Container {container_id} CPU pinned, escalating to SIGKILL")
        cmd_kill = ["docker", "kill", "--signal=SIGKILL", container_id]
        await run_cmd_async(cmd_kill)
    finally:
        # 容器带有 --rm，销毁后内核自动回收 cgroup 与 tmpfs
        logger.info(f"Container {container_id} completely eradicated")

绝对不仅在 Python 客户端执行 conn.close()。提前记录数据库后端连接的 PID，使用独立管理连接将其彻底终止。 

async def execute_sql_with_cancellation(query: str, token: CancellationToken):
    async with db_pool.acquire() as conn:
        # 记录该连接在 DB 底层的 backend_pid
        backend_pid = await conn.fetchval("SELECT pg_backend_pid()")
        token.register_resource("db_pid", backend_pid)
        
        try:
            return await conn.fetch(query)
        except asyncio.CancelledError:
            # 取消触发时，用独立连接下发取消指令
            async with admin_pool.acquire() as admin_conn:
                await admin_conn.execute(
                    "SELECT pg_cancel_backend($1)", backend_pid
                )
            logger.info(f"Killed slow SQL backend PID: {backend_pid}")
            raise

⚡ 线上防死循环与熔断三道防线

第 1 道防线：状态快照不可变（Frozen Snapshot）
AgentRuntimeLimits 采用 @dataclass(frozen=True) 修饰。每一次 Run 启动时由系统配置生成只读快照传入，运行中途模型任何 ToolCall 无法篡改自身的配额限制。
第 2 道防线：上下文滑动窗口智能压缩（Sliding Window Compaction）

第 3 道防线：双轨制超时控制（协作式中断 + 异步硬超时）

🔒 packages/data_gateway/sql_guard.py: SQLGlot AST 语法树安全护栏 数据安全基石

在数据分析系统中，大模型生成的 SQL 是不可信输入。单纯使用“正则黑名单过滤”在企业生产中极易被黑客或模型自身的意外输出绕过（如多行注释 /*...*/ 混淆、十六进制编码、盲注函数）。DataPilot 引入了工业级 SQLGlot AST（抽象语法树）解析器，在 SQL 投递到数据库之前执行多维严格静态分析。

🛡️ 语法树安全护栏的 5 重防线

1. 单一 Select 语句强校验 (Single Select)
语法树顶层根节点必须严格为 exp.Select 类型。遇到分号多语句（; DROP TABLE）、DML（INSERT/UPDATE/DELETE）、DDL（ALTER/DROP）一律直接阻断，从机制上杜绝篡改可能。
2. 危险函数 AST 深度遍历黑名单
遍历 AST 中所有 exp.Anonymous / exp.Func 节点。严厉封杀任何带有副作用或提权性质的函数：load_file, sleep, benchmark, httpfs, load_extension, read_csv, sqlite_scan 等。
3. 强制 LIMIT 夹持 (Limit Clamping)
无论模型是否写了 LIMIT，网关均强制介入：无 LIMIT 则自动在 AST 注入 LIMIT 200；若模型写了超过 1000 的 LIMIT，AST 强行改写将其夹持（Clamp）到 1000，杜绝全表扫描撑爆内存。
4. 真实元数据 Schema 校验
结合数据源的 SchemaSummaryRead，校验 SQL 引用的表名和列名是否真实存在。防止模型使用幻觉推测出的虚拟字段反复发起无效查询。

⚡ 错误可恢复性分流（Retryable vs Fatal）

在数据网关返回执行结果时，DataPilot 创新性地将错误分为可恢复（Retryable）与不可恢复（Fatal）：

  • Retryable 错误：包括 SQL_PARSE_ERROR, UNKNOWN_TABLE, UNKNOWN_COLUMN, INVALID_LIMIT。此类错误包含明确的语法树定位信息（行号、列号、缺失字段），系统将其作为明确的反馈喂给模型，允许最多 2 次自愈修复（SQL Repair）。
  • Fatal 错误：包括命中危险函数黑名单、非法 DDL/DML 尝试。系统直接熔断终止该工具路径，避免被恶意提示词注入进一步探测。

sql_guard.py (AST 解析、危险函数拦截与 LIMIT 夹持核心逻辑) 
from sqlglot import exp, parse
from sqlglot.optimizer.scope import traverse_scope

# 危险函数黑名单：封杀文件操作、时间盲注、未受控外部扫描
_DANGEROUS_FUNCTION_NAMES = {
    "load_file", "sleep", "benchmark", "httpfs",
    "load_extension", "read_csv", "read_parquet",
    "read_json", "parquet_scan", "sqlite_scan"
}

def inspect_sql(sql: str, dialect: str, schema: SchemaSummaryRead) -> SqlGuardResult:
    # 1. 解析为 AST 语法树，验证是否为单一合法语句
    statements = parse(sql, read=dialect)
    if len(statements) != 1:
        return SqlGuardResult(passed=False, code="MULTIPLE_STATEMENTS")
    
    ast = statements[0]
    # 2. 强校验必须是只读 Select
    if not isinstance(ast, exp.Select):
        return SqlGuardResult(passed=False, code="NON_SELECT_STATEMENT")

    # 3. 遍历语法树中所有调用的函数节点
    for node in ast.find_all(exp.Func):
        if node.name.lower() in _DANGEROUS_FUNCTION_NAMES:
            return SqlGuardResult(passed=False, code="DANGEROUS_FUNCTION_CALL")

    # 4. 强制 LIMIT 夹持：保证内存安全
    limit_node = ast.args.get("limit")
    if limit_node is None:
        ast = ast.limit(200)  # 缺省注入 200
    elif int(limit_node.expression.this) > 1000:
        ast.args["limit"] = exp.Limit(this=exp.Literal.number(1000))  # 强行夹持为 1000

    return SqlGuardResult(passed=True, sanitized_sql=ast.sql(dialect))

📋 packages/agent_runtime/analysis_planning.py: 分析规划与证据绑定 结构化语义

在传统无状态的 Agent 中，模型经常会产生“执行完查询就忘了目标是什么”或“查完 A 却回答了 B”的偏航问题。DataPilot 将用户分析诉求拆解为严格的形式化契约：Requirement（目标） ➔ Assertion（断言指标） ➔ EvidenceBinding（证据绑定）。

⛓️ 分析规划与证据绑定三元组

1. Requirement (用户目标)
将用户提问拆解为 1~N 个互不重叠的核心分析诉求。例如 req_1: "统计华东区 2026 年 Q1 总销售额"。
2. Assertion (事实断言)
为每个 Requirement 挂载强类型的指标断言。如 assert_total_gmv, assert_growth_rate，确保必须由具体数值填充。
3. EvidenceBinding (证据绑定)
将模型提取的数值与具体底层数据操作深度绑定，记录对应的 tool_call_id、执行 SQL、生成的数据集行号。

🚪 证据提交工具：模型不准跳步的核心关卡

在需要证据履约的分析计划中，当模型执行完 SQL 查询后，如果它企图直接用自然语言回答，会被当前回合的工具可见性和条件边拦截，先要求调用 commit_analysis_claims 完成证据绑定；普通问答不会伪造这条门禁。

⚠️ require_commit 拦截话术与注入机制

系统将自动向上下文注入一条结构化 Human 提示消息：
"当前仍未完成用户目标：[req_1]。已有证据应优先提交：本轮应先调用 commit_analysis_claims；尚未覆盖的断言必须单独提交，不能为了凑齐整条目标重复或编造值。"
这一硬约束彻底杜绝了模型在拿到数据后偷懒不存证据、或者脱离数据口胡推演的行为！

    self,
    workspace: ScriptWorkspace,
    container_name: str,

⚙️ 事件管道 5 大核心设计原则

核心机制 实现细节 解决的高并发与生产级难题
先入库，后通知 所有 RunEvent 必须先通过 SQLAlchemy 异步事务完整写入数据库 run_events 表并提交成功，随后才调用通知钩子唤醒 SSE 响应流。 彻底消除内存队列丢消息隐患。即使后端服务在通知前一瞬间遭遇 OOM 崩溃，重启后客户端依然能通过账本拉取完整历史。
严格单调自增序 每个运行任务由 _sequence_locks[run_id] 异步锁保护，在入库时严格分配自增 seq，数据库表建立 UNIQUE(run_id, seq) 复合约束。 防止异步并发执行工具或模型输出时，事件乱序到达前端导致 UI 倒放或状态竞争覆盖。
Last-Event-ID 毫秒重放 前端 EventSource 自动携带标准 Last-Event-ID 请求头，后端根据 seq > last_seen_seq 执行增量游标检索并立即回放。 用户在移动端弱网切换网络、页面 F5 强刷、或者跨标签页切换时，实现 100% 无感断点续传。
RunFinalizer 单终态原子锁 独立 run_finalizer.py 管理运行生命周期，定义 COMPLETED / FAILED / CANCELLED / TIMED_OUT 四大终态，通过原子 CAS 状态变更。 防止用户取消操作与后台模型输出完成发生冲突，杜绝系统同时发出两个互斥终态事件（如既 Success 又 Cancelled）。
防垃圾注入与尺寸熔断 通用事件 Payload 限制 8KB，Agent 单轮输出严格收紧至 16KB，报错诊断字段限制 500 字符，内部标识符采用正则 ^[A-Za-z0-9_.:-]{1,120}$ 校验。 彻底杜绝模型因幻觉疯狂吐出 Base64 脏数据或超长文本导致客户端 DOM 卡死或数据库存储爆炸。

async def append_run_event(
    session: AsyncSession,
    run_id: str,
    event_type: RunEventType,
    payload: dict[str, Any],
    *,
    notifier: _Notifier | None = None,
) -> RunEventRead:
    """向 Run 事件账本追加一条新事件：先入库，再通知 SSE。"""
    # 获取单 Run 专属序号互斥锁，确保并发安全且无空洞递增
    async with _sequence_locks[run_id]:
        stmt = select(func.coalesce(func.max(RunEventModel.seq), 0)).where(
            RunEventModel.run_id == run_id
        )
        current_seq = await session.scalar(stmt)
        next_seq = (current_seq or 0) + 1

        # 数据消毒与尺寸安全核验
        sanitized_payload = _sanitize_payload(event_type, payload)
        event_id = make_id("evt")
        
        event_record = RunEventModel(
            id=event_id,
            run_id=run_id,
            seq=next_seq,
            event_type=event_type.value,
            payload=sanitized_payload,
            created_at=utc_now(),
        )
        session.add(event_record)
        await session.commit()   # 事务严格落地

    # 入库成功后再通知外部观察者（SSE 管道）
    if notifier is not None:
        await notifier(run_id)

    return RunEventRead.model_validate(event_record)

export function subscribeRunEvents(
  runId: string,
  onEvent: (event: RunEvent) => void,
  lastSeenSeq: number = 0
): () => void {
  let cursor = lastSeenSeq;
  const url = `/api/runs/${runId}/events?after_seq=${cursor}`;
  const eventSource = new EventSource(url);

  eventSource.onmessage = (e) => {
    const payload = JSON.parse(e.data) as RunEvent;
    if (payload.seq > cursor) {
      cursor = payload.seq;
      onEvent(payload);
    }
  };

  eventSource.onerror = () => {
    // 由客户端重连策略重新订阅，并带上当前最新 after_seq cursor，避免重复投影
    console.warn("SSE stream disconnected. Re-synchronizing from sequence:", cursor);
  };

  return () => eventSource.close();
}

🧠 Session、Memory 与数据源隔离Aggregate boundary

Session 是 Run、消息、历史答案摘要、Artifact 和工作区的聚合边界。会话连续性可以保留近期消息和偏好，但不能把旧 DataSource 的事实带入新 Run。

场景系统动作不能发生的事
新建 Run读取当前 Session DataSource，创建只读输入快照，记录上下文 revision读取其他 Run 的原始输入或 Artifact 事实
消息窗口首屏最近消息；before_position 向上加载；items 仍按旧到新前端自行重排或复制一套消息事实
切换 DataSource阻止活跃 Run，之后新 Run 使用新快照和新事实范围召回旧数据源的指标、文件或答案事实
删除 Session协调活跃 Run 收尾并清理 Metadata、Artifact、工作区留下可继续回放的孤立历史入口
事实隔离：Session memory 只用于理解追问、偏好和待办；它不是数据事实来源，不能替代当前 Run 的 Schema、SQL Audit 或 Artifact 证据。
